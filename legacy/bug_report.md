# DTUG IDE 潜在 Bug 分析报告

> 排除已知三个问题（行末空格/换行 WA、编码问题、无法评测）后，通过静态代码分析发现的其他潜在缺陷与复现方法。

---

## 一、严重功能性缺陷（可导致误判或死锁）

### 1. /judge 路由存在 pipe 死锁，导致正确程序被误判 TLE

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` `judge_code()` 第 306-345 行 |
| **根因** | `while proc.poll() is None:` 循环仅轮询进程状态与内存，**从未读取 `stdout` 或 `stderr`**。当子进程输出量超过 OS pipe 缓冲区（Windows 上通常 4 KB-64 KB）时，`write()` 阻塞，进程永不结束，最终被判定 **TLE**。 |
| **影响** | 输出量稍大的正确程序（如打印 1000 行以上）会被误判超时。 |

**复现方法**：
1. 打开 `/judge` 页面。
2. 导入任意测试数据。
3. 提交如下代码：
```cpp
#include <iostream>
int main() {
    for (int i = 0; i < 5000; ++i)
        std::cout << i << " hello world\n";
    return 0;
}
```
4. 设置时间限制为 3 s，开始评测。
5. 结果：**TLE**，但程序实际应瞬间完成。

### 2. 编译器选择器前端传参，后端完全忽略

| 项目 | 说明 |
|------|------|
| **位置** | `index.html` 第 1030-1033 行；`app.py` 第 59-66 行、第 141-147 行、第 237 行 |
| **根因** | 前端 `compilerSelect` 可选 `g++` / `g++-13`，并通过 `/compile`、`/test`、`/judge` 的 `compiler` 字段提交，但后端所有编译命令均硬编码为 `['g++', ...]`，未读取 `data.get('compiler')`。 |
| **影响** | 用户切换编译器无效，若系统默认 `g++` 版本过旧（不支持 `-std=c++17`），则编译失败，用户无法通过界面指定其他版本。 |

**复现方法**：
1. 在 `index.html` 中将 `compilerSelect` 设为 `g++-13`（假设已安装）。
2. 提交任意 C++17 代码。
3. 在 `app.py` 中打印 `data` 发现 `compiler` 字段存在，但后端仍调用 `g++`。

---

### 3. 评测后残留进程未清理（`TimeoutExpired` 未 kill）

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 第 76-77 行（compile）、第 156-157 行（test）、第 182-183 行（test 运行） |
| **根因** | 捕获 `subprocess.TimeoutExpired` 后，仅返回错误信息，**未对子进程执行 `kill()`**。编译进程或运行进程仍留在后台，持续占用文件句柄与 CPU。 |
| **影响** | 多次触发超时后，系统残留僵尸进程；Windows 上临时目录的 `.exe` 被占用，导致后续清理失败。 |

**复现方法**：
1. 提交如下死循环代码到 `/test`：
```cpp
#include <iostream>
int main() { while (true); }
```
2. 触发 10 s 运行超时。
3. 在任务管理器或 `tasklist | findstr exe` 中观察，进程仍然存活。

---

### 4. `/judge` 预热进程未执行 `wait()`，残留僵尸进程

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 第 260-277 行 |
| **根因** | `warmup_proc` 在超时分支调用了 `wait()`，但在**正常结束分支**没有 `wait()`。 |
| **影响** | 预热进程成为僵尸进程，句柄未释放。 |

---

### 5. `/test` 与 `/judge` 的 RE 判定将 `stderr` 混入 `stdout` 比对

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 第 182 行（test）、第 361 行（judge） |
| **根因** | 判定时 `output = stdout + stderr`（或 `actual = stdout + stderr`），stderr 的警告信息被当作程序输出与 expected 比较。 |
| **影响** | 即使 `stdout` 完全正确，只要 `stderr` 有编译警告或运行时警告（如 MinGW 的某些库输出），就会判为 WA。 |

**复现方法**：
1. 提交一段会产生 `stderr` 的代码到 `/judge`：
```cpp
#include <iostream>
int main() {
    std::cerr << "Warning: debug\n";
    std::cout << "3" << std::endl;
    return 0;
}
```
2. 期望输出为 `3`。
3. 结果被判 **WA**（实际输出包含 `Warning: debug\n3`）。

## 二、Windows 平台特有问题

### 6. `subprocess` 默认编码导致中文乱码 / `UnicodeDecodeError`

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 所有 `subprocess.run(..., text=True, ...)` 与 `subprocess.Popen(..., text=True, ...)` |
| **根因** | Windows 系统默认编码为 `cp936`（GBK），但用户 C++ 代码可能以 UTF-8 输出中文。`text=True` 时 Python 使用系统编码解码，导致**乱码**或抛出 `UnicodeDecodeError`。 |
| **影响** | 程序输出含中文即报错；judge 页面直接 500 错误。 |

**复现方法**：
1. 提交代码：
```cpp
#include <iostream>
int main() {
    std::cout << "你好，世界" << std::endl;
    return 0;
}
```
2. 在 `/test` 运行。
3. 后端抛出 `UnicodeDecodeError: 'gbk' codec can't decode byte 0x...`。若未抛异常，前端也会显示乱码。

---

### 7. `/compile` 启动独立 CMD 窗口时路径未转义

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 第 93 行 |
| **根因** | `cmd = f'start "C++ 程序" /D "{TEMP_DIR}" cmd /c "{exe_file} && pause"'`，如果 `TEMP_DIR` 或 `exe_file` 包含**空格**或 `&` 等特殊字符，会被 `cmd.exe` 错误解析。 |
| **影响** | 项目路径若位于 `D:\Program Files\...` 或含 `&`，命令执行失败。 |

**复现方法**：
1. 将项目移动到 `D:\My IDE\` 目录下运行。
2. 执行「编译运行」。
3. CMD 窗口报错：找不到路径或意外执行了 `&&` 后的命令。

---

### 8. 测试结束后临时 `.exe` 文件残留（Windows 文件锁）

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 第 203-207 行（test）、第 390-394 行（judge） |
| **根因** | Windows 下运行中的 `.exe` 被占用，如果进程因超时未 kill（Bug 3），或独立 CMD 窗口仍打开，`os.remove(exe_file)` 会抛出 `PermissionError`。异常被 `except: pass` 吞掉。 |
| **影响** | `temp_compile` 目录逐渐膨胀，最终可能耗尽磁盘。 |

## 三、安全性与边界问题

### 9. 无沙箱隔离，用户代码可任意读写服务器文件

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 所有运行逻辑 |
| **根因** | 编译运行的进程直接使用当前用户权限，未限制文件系统、网络、注册表访问。 |
| **影响** | 恶意或误操作代码可删除工作目录文件、读取敏感信息、发起网络请求。 |

**复现方法**：
1. 提交以下代码到 `/compile` 或 `/judge`：
```cpp
#include <cstdlib>
int main() {
    system("del /Q ..\\*.py");   // 或 system("shutdown /s /t 0");
    return 0;
}
```
2. 编译运行后，工作目录文件被删除。

---

### 10. 前端 `judge.html` 测试用例名未转义，存在 XSS 风险

| 项目 | 说明 |
|------|------|
| **位置** | `judge.html` 第 872 行 |
| **根因** | `div.innerHTML = \`<span class="name">${tc.name}</span>\``，如果文件名包含 `<script>` 或 `</div>` 等 HTML 标签，会注入到页面。 |
| **影响** | 导入文件夹中若存在名为 `test<script>alert(1)</script>.in` 的文件，页面执行任意脚本。 |

**复现方法**：
1. 在测试文件夹中创建文件名为 `<img src=x onerror=alert(1)>.in` 及对应的 `.ans`。
2. 在 `/judge` 页面导入该文件夹。
3. 触发 XSS 弹窗。

---

### 11. `time_limit` / `memory_limit` 未做有效校验

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 第 226-227 行 |
| **根因** | `float(data.get('time_limit', 1.0))` 允许传入负数、`NaN` 或极大值，导致 `while` 循环立即判 TLE 或永不超时。 |
| **影响** | 前端可构造恶意请求使后端进入死循环或无限等待。 |

**复现方法**：
1. 直接构造 POST `/judge` 请求：`{"time_limit": -1, ...}`。
2. 程序立即被判定 TLE（时间为负时 `elapsed > -1` 恒成立）。
3. 或传入 `time_limit: 999999` 使进程运行极长时间。

---

### 12. `judge.html` 文件导入时，`base` 提取逻辑对无扩展名文件出错

| 项目 | 说明 |
|------|------|
| **位置** | `judge.html` 第 750-751 行、第 802-803 行 |
| **根因** | `base = name.slice(0, name.lastIndexOf('.'))`，如果文件名为 `.in` 或 `.ans`，`lastIndexOf('.')` 返回 0，`base` 变为空字符串 `''`。 |
| **影响** | 无扩展名或仅有扩展名的文件被错误解析，测试用例列表中显示空名称。 |

**复现方法**：
1. 在测试文件夹中创建文件 `.in` 和 `.ans`。
2. 导入后 `fileMap` 中 `base` 为空字符串，界面显示空白测试用例名。

---

### 13. 测试用例导入顺序不可控（非字母/数字排序）

| 项目 | 说明 |
|------|------|
| **位置** | `judge.html` 第 764-772 行、第 832-834 行 |
| **根因** | `Object.entries(fileMap)` 不保证按键名排序。OI 评测中通常需要 `1.in`, `2.in`, `10.in` 按字典序或自然序排列。 |
| **影响** | 测试用例顺序混乱，用户无法判断哪一组失败。 |

## 四、前端与状态管理缺陷

### 14. `judge.html` 中引用不存在的 DOM 元素 `consoleBody`

| 项目 | 说明 |
|------|------|
| **位置** | `judge.html` 第 630 行 |
| **根因** | `const consoleBody = document.getElementById('consoleBody');` 获取 `null`，因为 judge 页面没有该元素。虽然后续代码未使用 `consoleBody`，但属于未清理的残留引用。 |
| **影响** | 若后续扩展功能误用 `consoleBody`，立即抛出 `TypeError`。 |

---

### 15. `/judge` 编译错误时不展示编译输出信息

| 项目 | 说明 |
|------|------|
| **位置** | `judge.html` 第 928-940 行 |
| **根因** | 后端返回 `compile_output` 字段，但前端仅将每个测试点标记为 `CE`，未将 `compile_output` 渲染到页面任何位置。 |
| **影响** | 用户无法看到编译错误日志，只能盲猜。 |

**复现方法**：
1. 在 `/judge` 页面提交语法错误的 C++ 代码。
2. 点击「开始评测」。
3. 所有测试点显示 `CE`，但无任何编译错误提示。

---

### 16. `temp_compile` 启动清理不彻底（只删文件，不删子目录）

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 第 23-27 行 |
| **根因** | 使用 `os.remove()` 遍历目录，若目录中有子目录或只读文件，`os.remove()` 抛异常被吞掉，子目录残留。 |
| **影响** | 目录膨胀；若子目录中意外存在同名 `.exe` 可能与后续 UUID 冲突。 |

---

### 17. 测试点之间无隔离（文件系统状态共享）

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` `/judge` 所有测试点循环 |
| **根因** | 所有测试点使用同一个 `.exe`，且 C++ 代码可以在运行期间读写当前工作目录（即 `temp_compile`）中的文件。 |
| **影响** | 若用户代码写入文件 `a.txt`，测试点 1 执行后，测试点 2 会读取到测试点 1 留下的数据，导致后续测试点结果错误。 |

**复现方法**：
1. 提交以下代码：
```cpp
#include <iostream>
#include <fstream>
int main() {
    std::ifstream in("a.txt");
    int x = 0;
    if (in >> x) std::cout << x;
    else std::cout << "0";
    std::ofstream out("a.txt");
    out << "999";
    return 0;
}
```
2. 测试点 1 期望输出 `0`，测试点 2 期望输出 `0`。
3. 实际测试点 2 输出 `999`（受测试点 1 污染），判 **WA**。

---

### 18. `/compile` 独立 CMD 窗口中 `&& pause` 对程序退出码非 0 时行为异常

| 项目 | 说明 |
|------|------|
| **位置** | `app.py` 第 93 行 |
| **根因** | `cmd /c "{exe_file} && pause"` 中，`&&` 要求前一个命令返回码为 0 才会执行 `pause`。若程序 `return 1` 或崩溃，`pause` 不会执行，窗口一闪而过。 |
| **影响** | 用户无法看到运行错误或异常退出的信息。 |

**复现方法**：
1. 提交 `return 1;` 或 `abort();` 的代码，执行「编译运行」。
2. 窗口立即关闭，无法查看错误。
